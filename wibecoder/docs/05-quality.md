# 05. Система качества

## 5.1. Зачем

Качество — **главный навык заказчика** и главный критерий оплаты. Из концепта: «на более сложных и дорогих заказах есть ограничения на дедлайн и на качество игры, причём качество — это совокупность параметров: музыка, графика, геймплей и прочее». Система делает это буквальным: у проекта 7 подсистем, у заказа — требования к сумме и точечные.

## 5.2. Подсистемы качества

| Ключ | Название | Что «на самом деле» | Базовая потребность `need` (тир 1) |
| :--- | :--- | :--- | :--- |
| `graphics` | Графика | Арт, визуал, эффекты | 60 |
| `gameplay` | Геймплей / Логика | Механики, сценарии, «интересность» | 70 |
| `music` | Музыка и звук | Треки, SFX, аудио-картина | 50 |
| `code` | Код (стабильность) | Отсутствие багов, надёжность | 80 |
| `ux` | UX / Интерфейс | Удобство, вёрстка, навигация | 55 |
| `perf` | Оптимизация | FPS, размер, батарея | 45 |
| `docs` | Документация | ТЗ, инструкции, комментарии (важно для САПР) | 40 |

`need` масштабируется: `need_i = base_need_i * tier_factor * project_size`, где `tier_factor` ≈ ×1.8 за тир (см. [14](14-balance.md)).

## 5.3. Веса подсистем по типам проектов

`Q_total = Σ (w_i * q_i)`, веса нормированы (Σw = 1):

| Подсистема | 🎮 Игра | 🌐 Сайт | 📱 Приложение | ⚙️ САПР |
| :--- | :--- | :--- | :--- | :--- |
| graphics | 0.25 | 0.20 | 0.15 | 0.05 |
| gameplay | 0.30 | 0.05 | 0.10 | 0.15 |
| music | 0.20 | 0.05 | 0.05 | 0.00 |
| code | 0.15 | 0.25 | 0.30 | 0.35 |
| ux | 0.05 | 0.30 | 0.25 | 0.10 |
| perf | 0.05 | 0.10 | 0.15 | 0.20 |
| docs | 0.00 | 0.05 | 0.00 | 0.15 |

Веса переопределяются на уровне заказа (например, «музыкальная игра»: music ×1.5 с перенормировкой).

## 5.4. Итоговая оценка проекта

```python
Q_total   = sum(w[type][i] * q[i] for i in subsystems)     # 0..100
Q_final   = Q_total - 3 * bugs_left                        # незакрытые косяки
# точечные требования (из ТЗ):
meets_sub = all(q[i] >= req.sub[i] for i in req.sub)
```

## 5.5. Приёмка заказчиком

| Условие | Результат |
| :--- | :--- |
| `Q_final ≥ req.total` И `meets_sub` | **Принято**: полная оплата, +репутация |
| `Q_final ≥ 1.15 * req.total` И `meets_sub` | **«Золотой проект»**: оплата ×1.25, +репутация +3, открывает «постоянного клиента» |
| `req.total ≤ Q_final < 1.15*req.total`, но точечные требования провалены | **«Доделать»**: 1 бесплатная итерация правок (1 игровой день), иначе −25% оплаты |
| `0.7 * req.total ≤ Q_final < req.total` | **Принято с бубнами**: оплата ×0.5, −репутация −2 |
| `Q_final < 0.7 * req.total` | **Отказ**: оплата 0, −репутация −5, заказчик «в чёрный список» |

## 5.6. Формула оплаты

```python
quality_mult = 0.4 + 0.6 * (Q_final / req.total)       # кап 1.0 (бонус выше — отдельно)
deadline_mult = see(таблица в 03-orders.md §3.6)        # 1.0 / 0.7 / 0.4 / 0.15
rep_mult      = 1 + reputation * 0.005
gold_bonus    = 1.25 if golden_project else 1.0

payout = base_price * min(quality_mult, 1.0) * deadline_mult * rep_mult * gold_bonus
xp_gain = project_complexity * (Q_final / 50)           # скиллы — см. [06]
```

## 5.7. Правки после сдачи (итерации)

- Заказчик может вернуть проект на доработку **1 раз** («доделать»): те же требования +1 игровой день, но каждая правка тратит токены/время как обычная генерация.
- Второй возврат = автоматически «принято с бубнами» или отказ.

## 5.8. Видимость качества для игрока

- На экране проекта — **7 полосок** подсистем с текущими `q_i`, требованиями заказа (пунктирные метки) и подсветкой «красное: ниже требований».
- Прогноз: «если влить ещё N токенов в графику → ожидаемый прирост +K (±шум)» — честный прогноз с учётом убывающей отдачи (без учёта рандома ±10%).
- После сдачи — **отчёт заказчика**: радар-чарт подсистем + цитата («Звук — кринж, но играется норм», «Документация — топ, возьму на следующий проект»).

## 5.9. Скрытые взаимосвязи

- `music` и `gameplay` слабо синергируют: если оба > 70 — «вау-эффект» +3% к `Q_total` («игра качает»).
- `perf` влияет на шанс «заказчик вернулся с багом» после сдачи (низкая оптимизация → ивент «скинули баг-репорт», −репутация).
- `docs` критично для САПР и корпоратива (типичные точечные требования `docs ≥ 50`).

## 5.10. Пример расчёта (порядок цифр)

Проект: игра (тир 2), требования: total 45, music ≥ 50. Игрок влил токены, получил: graphics 40, gameplay 55, music 38, code 50, ux 35, perf 30, docs 20.

```
Q_total = .25*40 + .30*55 + .20*38 + .15*50 + .05*35 + .05*30 + .0*20
        = 10 + 16.5 + 7.6 + 7.5 + 1.75 + 1.5 = 44.85
bugs_left = 2 → Q_final = 44.85 − 6 = 38.85
music (38) < 50 → точечное требование провалено
→ «Доделать» (1 итерация) либо принятие ×0.5
```

Урок для игрока: **не жадничать на музыке, когда заказчик просил музыку**.
